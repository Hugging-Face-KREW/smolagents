# 에이전트란? 🤔

## 에이전트 시스템 소개

AI를 사용하는 모든 효율적인 시스템은 LLM에 실제 세계에 대한 어떤 종류의 액세스를 제공해야 합니다. 예를 들어, 외부 정보를 얻기 위해 검색 도구를 호출할 수 있는 기능이나 작업을 해결하기 위해 특정 프로그램에 작용할 수 있는 기능이 있습니다. 즉, LLM은 ***에이전시***를 가져야 합니다. 에이전트 프로그램은 LLM의 외부 세계로 통하는 관문입니다.

> [!TIP]
> AI 에이전트는 **LLM 출력이 워크플로우를 제어하는 프로그램입니다**.

LLM을 활용하는 모든 시스템은 LLM 출력을 코드에 통합합니다. LLM의 입력이 코드 워크플로우에 미치는 영향은 시스템에서 LLM의 에이전시 수준입니다.

이 정의에서 "에이전트"는 이산적인 0 또는 1 정의가 아니라는 점에 유의하세요. 대신 "에이전시"는 워크플로우에서 LLM에 더 많거나 적은 힘을 주면서 연속적인 스펙트럼으로 진화합니다.

아래 표에서 에이전시가 시스템마다 어떻게 달라질 수 있는지 보세요:

| 에이전시 수준 | 설명                                                         | 짧은 이름        | 예제 코드                                          |
| ------------ | ------------------------------------------------------------ | --------------- | -------------------------------------------------- |
| ☆☆☆          | LLM 출력이 프로그램 흐름에 영향을 미치지 않음                  | Simple processor | `process_llm_output(llm_response)`                 |
| ★☆☆          | LLM 출력이 if/else 스위치를 제어함                           | Router           | `if llm_decision(): path_a() else: path_b()`       |
| ★★☆          | LLM 출력이 함수 실행을 제어함                                | Tool call        | `run_function(llm_chosen_tool, llm_chosen_args)`   |
| ★★☆          | LLM 출력이 반복 및 프로그램 연속을 제어함                    | Multi-step Agent | `while llm_should_continue(): execute_next_step()` |
| ★★★          | 한 에이전트 워크플로우가 다른 에이전트 워크플로우를 시작할 수 있음 | Multi-Agent      | `if llm_trigger(): execute_agent()`                |
| ★★★          | LLM이 코드에서 작동하고 자신의 도구를 정의하거나 다른 에이전트를 시작할 수 있음 | Code Agents      | `def custom_tool(args): ...`                       |

다단계 에이전트는 이러한 코드 구조를 가지고 있습니다:

```python
memory = [user_defined_task]
while llm_should_continue(memory): # 이것은 다단계 부분입니다
    action = llm_get_next_action(memory) # 이것은 도구 호출 부분입니다
    observations = execute_action(action)
    memory += [action, observations]
```

이 에이전트 시스템은 루프에서 실행되며, 각 단계에서 새로운 작업을 실행합니다(작업은 단순히 함수인 사전 결정된 *도구* 호출과 관련될 수 있음). 관찰이 주어진 작업을 해결하기 위해 만족스러운 상태에 도달한 것이 명백해질 때까지 실행됩니다. 다단계 에이전트가 간단한 수학 문제를 어떻게 해결할 수 있는지의 예는 다음과 같습니다:

## ✅ 에이전트를 사용할 때 / ⛔ 피해야 할 때

에이전트는 LLM이 앱의 워크플로우를 결정하는 데 필요할 때 유용합니다. 하지만 종종 과도합니다. 질문은 다음과 같습니다: 정말로 현재 작업을 효율적으로 해결하기 위해 워크플로우에 유연성이 필요합니까?
사전 결정된 워크플로우가 너무 자주 부족하면 더 많은 유연성이 필요하다는 의미입니다.
예를 들어보겠습니다: 서핑 여행 웹사이트에서 고객 요청을 처리하는 앱을 만들고 있다고 가정해봅시다.

요청이 2개 버킷 중 하나에 속한다는 것을 미리 알 수 있고(사용자 선택에 따라), 이 2개 경우 각각에 대해 사전 정의된 워크플로우가 있습니다.

1. 여행에 대한 지식을 원하십니까? ⇒ 지식 기반을 검색할 수 있는 검색 표시줄에 액세스하도록 하세요
2. 판매팀과 대화하고 싶으세요? ⇒ 연락 양식을 입력하도록 하세요.

그 결정론적 워크플로우가 모든 쿼리에 맞다면, 모든 것을 코딩하세요! 이것은 예측할 수 없는 LLM이 워크플로우에 간섭하게 함으로써 오류가 발생할 위험이 없는 100% 신뢰할 수 있는 시스템을 제공합니다. 단순성과 견고성을 위해 에이전트 동작을 사용하지 않도록 정규화하는 것이 좋습니다.

하지만 워크플로우를 미리 그렇게 잘 결정할 수 없다면 어떻게 될까요?

예를 들어, 사용자가 다음과 같이 물어보기를 원합니다: `"월요일에 올 수 있지만 여권을 잊어버려 수요일까지 지연될 위험이 있습니다. 화요일 아침에 나와 내 짐을 서핑할 수 있고 취소 보험이 있을까요?"` 이 질문은 많은 요소에 달려 있으며 위의 사전 결정된 기준 중 아무것도 이 요청에 충분하지 않을 것입니다.

사전 결정된 워크플로우가 너무 자주 부족하면 더 많은 유연성이 필요하다는 의미입니다.

이것이 에이전트 설정이 도움이 되는 곳입니다.

위의 예에서 날씨 예측을 위한 날씨 API, 이동 거리를 계산하기 위한 Google Maps API, 직원 가용성 대시보드 및 지식 기반의 RAG 시스템에 액세스할 수 있는 다단계 에이전트를 만들 수 있습니다.

최근까지 컴퓨터 프로그램은 사전 결정된 워크플로우로 제한되었으며 if/else 스위치를 쌓아서 복잡성을 처리하려고 했습니다. 그들은 "이 숫자의 합을 계산하세요" 또는 "이 그래프에서 가장 짧은 경로를 찾으세요"와 같은 극도로 좁은 작업에 중점을 두었습니다. 하지만 실제로 우리의 여행 예제와 같은 대부분의 실제 작업은 사전 결정된 워크플로우에 맞지 않습니다. 에이전트 시스템은 프로그램에 광대한 실제 작업의 세계를 열어줍니다!

## `smolagents`는 왜일까요?

체인이나 라우터와 같은 일부 저수준 에이전트 사용 사례의 경우 모든 코드를 직접 작성할 수 있습니다. 이렇게 하면 시스템을 더 잘 제어하고 이해할 수 있으므로 훨씬 더 좋을 것입니다.

하지만 LLM이 함수를 호출하게 하는 것("도구 호출")이나 LLM이 while 루프를 실행하게 하는 것("다단계 에이전트")과 같은 더 복잡한 동작으로 시작하면 일부 추상화가 필요합니다:
- 도구 호출의 경우 에이전트의 출력을 파싱해야 하므로 이 출력은 "Thought: I should call tool 'get_weather'. Action: get_weather(Paris)."와 같은 사전 정의된 형식이 필요하며, 이를 사전 정의된 함수로 파싱하고 LLM에 제공된 시스템 프롬프트가 이 형식을 알려야 합니다.
- LLM 출력이 루프를 결정하는 다단계 에이전트의 경우 마지막 루프 반복에서 무엇이 발생했는지에 따라 LLM에 다른 프롬프트를 제공해야 하므로 어떤 종류의 메모리가 필요합니다.

보세요? 이 두 가지 예제만으로도 이미 우리를 도울 필요가 있는 몇 가지 항목을 찾았습니다:

- 물론 시스템을 구동하는 엔진으로 작용하는 LLM
- 에이전트가 액세스할 수 있는 도구 목록
- 에이전트 논리에서 LLM을 안내하는 시스템 프롬프트: Reflection -> Action -> Observation의 ReAct 루프, 사용 가능한 도구, 사용할 도구 호출 형식...
- LLM 출력에서 도구 호출을 추출하는 파서(위의 시스템 프롬프트로 표시된 형식)
- 메모리

하지만 결정에서 LLM에 회의실을 주면 실수를 할 것이 분명합니다: 그러므로 우리는 오류 로깅 및 재시도 메커니즘이 필요합니다.

이 모든 요소들은 잘 기능하는 시스템을 만들기 위해 긴밀한 결합이 필요합니다. 그래서 우리는 모든 것이 함께 작동하도록 기본 구성 요소를 만들어야 한다고 결정했습니다.

## 코드 에이전트

다단계 에이전트에서 각 단계에서 LLM은 외부 도구에 대한 일부 호출 형태로 작업을 작성할 수 있습니다. 이러한 작업을 작성하기 위한 일반적인 형식(Anthropic, OpenAI 및 많은 다른 사람들이 사용)은 일반적으로 "도구 이름 및 사용할 인수의 JSON을 작성하고 어떤 도구를 실행할지 그리고 어떤 인수로 실행할지 알기 위해 이를 파싱"하는 다양한 음영입니다.

[여러](https://huggingface.co/papers/2402.01030) [연구](https://huggingface.co/papers/2411.01747) [논문](https://huggingface.co/papers/2401.00812)에서 LLM 작업을 코드 스니펫으로 작성하는 것이 더 자연스럽고 유연한 작성 방법임을 보여주었습니다.

이것의 이유는 단순히 *우리가 컴퓨터에서 수행하는 작업을 표현하기 위해 특별히 코드 언어를 만들었기* 때문입니다.
즉, 우리의 에이전트는 사용자의 문제를 해결하기 위해 프로그램을 작성할 것입니다: Python 또는 JSON의 블록에서 프로그래밍이 더 쉬울 것이라고 생각하시나요?

아래 그림은 [실행 가능한 코드 작업이 더 나은 LLM 에이전트를 유도합니다](https://huggingface.co/papers/2402.01030)에서 가져온 것으로, 코드에서 작업을 작성할 때의 일부 이점을 보여줍니다:

<img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/transformers/code_vs_json_actions.png">

코드가 아닌 JSON과 유사한 스니펫에서 작업을 작성하면 더 나은 결과를 제공합니다:

- **구성성:** JSON 작업을 서로 중첩하거나 나중에 다시 사용할 JSON 작업 세트를 정의할 수 있습니까? Python 함수를 정의할 수 있는 것처럼?
- **객체 관리:** `generate_image`와 같은 작업의 출력을 JSON에 어떻게 저장합니까?
- **일반성:** 코드는 컴퓨터가 할 수 있는 모든 것을 간단히 표현하도록 만들어졌습니다.
- **LLM 훈련 데이터의 표현:** 충분한 품질의 코드 작업이 이미 LLM의 훈련 데이터에 포함되어 있으므로 이미 이것에 대해 훈련되었습니다!
