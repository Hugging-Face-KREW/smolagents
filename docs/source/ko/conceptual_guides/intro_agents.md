# 에이전트란 무엇인가요? 🤔

## 에이전틱 시스템 소개

AI를 사용하는 효율적인 모든 시스템은 LLM에 실제 세계에 대한 일종의 접근을 제공해야 합니다. 예를 들어, 외부 정보를 얻기 위해 검색 도구를 호출할 수 있거나, 작업을 해결하기 위해 특정 프로그램에 작용할 수 있습니다. 다시 말해서, LLM은 ***에이전시***를 가져야 합니다. 에이전틱 프로그램은 LLM이 외부 세계에 접근하는 관문입니다.

> [!TIP]
> AI 에이전트는 **LLM 출력이 워크플로우를 제어하는 프로그램**입니다.

LLM을 활용하는 모든 시스템은 LLM 출력을 코드에 통합합니다. LLM 입력이 코드 워크플로우에 미치는 영향은 시스템에서 LLM의 에이전시 수준입니다.

이 정의에서 "에이전트"는 이산적인 0 또는 1 정의가 아니라는 점을 주목하세요. 대신 "에이전시"는 워크플로우에서 LLM에 더 많거나 적은 힘을 주면서 연속적인 스펙트럼을 따라 진화합니다.

아래 표에서 에이전시가 시스템 전체에서 어떻게 다양할 수 있는지 보세요:

| 에이전시 수준 | 설명                                                        | 짧은 이름        | 코드 예제                                          |
| ------------ | --------------------------------------------------------- | --------------- | -------------------------------------------------- |
| ☆☆☆          | LLM 출력이 프로그램 흐름에 영향을 미치지 않음                | 간단한 프로세서  | `process_llm_output(llm_response)`                 |
| ★☆☆          | LLM 출력이 if/else 스위치를 제어                           | 라우터           | `if llm_decision(): path_a() else: path_b()`       |
| ★★☆          | LLM 출력이 함수 실행을 제어                                | 도구 호출        | `run_function(llm_chosen_tool, llm_chosen_args)`   |
| ★★☆          | LLM 출력이 반복 및 프로그램 계속을 제어                    | 다중 단계 에이전트 | `while llm_should_continue(): execute_next_step()` |
| ★★★          | 하나의 에이전틱 워크플로우가 다른 에이전틱 워크플로우를 시작 | 멀티 에이전트    | `if llm_trigger(): execute_agent()`                |
| ★★★          | LLM이 코드에서 작동하고, 자체 도구를 정의하거나 다른 에이전트를 시작 | 코드 에이전트    | `def custom_tool(args): ...`                       |

다중 단계 에이전트는 이 코드 구조를 가집니다:

```python
memory = [user_defined_task]
while llm_should_continue(memory): # 이것이 다중 단계 부분입니다
    action = llm_get_next_action(memory) # 이것이 도구 호출 부분입니다
    observations = execute_action(action)
    memory += [action, observations]
```

이 에이전틱 시스템은 루프에서 실행되며, 각 단계에서 새로운 액션을 실행합니다(액션은 미리 결정된 *도구*(단순 함수)를 호출하는 것을 포함할 수 있음). 관찰이 주어진 작업을 해결하기 위해 만족스러운 상태에 도달했음이 명백해질 때까지 계속합니다. 다중 단계 에이전트가 간단한 수학 질문을 해결할 수 있는 방법의 예는 다음과 같습니다:

## ✅ 에이전트를 사용해야 할 때 / ⛔ 피해야 할 때

에이전트는 LLM이 앱의 워크플로우를 결정해야 할 때 유용합니다. 하지만 종종 과도합니다. 질문은 다음과 같습니다: 주어진 작업을 효율적으로 해결하기 위해 워크플로우에서 정말로 유연성이 필요한가요?
미리 정해진 워크플로우가 너무 자주 부족하다면, 더 많은 유연성이 필요합니다.
예를 들어, 서핑 여행 웹 사이트에서 고객 요청을 처리하는 앱을 만들고 있다고 가정하세요.

요청이 2개의 버킷(사용자 선택에 따라) 중 하나에 속할 것을 미리 알 수 있고, 이 2개 케이스 각각에 대해 미리 정의된 워크플로우가 있을 수 있습니다.

1. 여행에 대한 지식을 원하세요? ⇒ 지식 기반을 검색할 수 있는 검색 창에 접근할 수 있습니다
2. 영업 부서와 대화하고 싶으세요? ⇒ 연락 양식에 입력하도록 합니다.

그 결정론적 워크플로우가 모든 쿼리에 맞다면, 모든 것을 코드로 작성하세요! 이것은 예측 불가능한 LLM이 워크플로우에 개입하여 발생하는 오류의 위험이 없는 100% 안정적인 시스템을 제공합니다. 단순성과 강건성을 위해 에이전틱 동작을 사용하지 않는 방향으로 정규화하는 것이 좋습니다.

그런데 워크플로우를 미리 그렇게 잘 결정할 수 없다면 어떨까요?

예를 들어, 사용자가 다음을 묻고 싶어합니다: `"나는 월요일에 올 수 있지만, 여권을 잊어버려서 수요일까지 지연될 위험이 있습니다. 화요일 아침에 나와 내 물건을 서핑하러 데려갈 수 있을까요, 취소 보험이 있으면요?"` 이 질문은 많은 요소에 달려 있으며, 아마도 위의 미리 정해진 기준 중 어느 것도 이 요청에 충분하지 않을 것입니다.

미리 정해진 워크플로우가 너무 자주 부족하다면, 더 많은 유연성이 필요합니다.

이것이 에이전틱 설정이 도움이 되는 곳입니다.

위의 예에서, 날씨 API에 접근하여 날씨 예보를 제공하고, Google Maps API로 여행 거리를 계산하며, 직원 가용성 대시보드 및 지식 기반에 대한 RAG 시스템이 있는 다중 단계 에이전트를 만들 수 있습니다.

최근까지, 컴퓨터 프로그램은 미리 결정된 워크플로우로 제한되었으며, if/else 스위치를 쌓아서 복잡성을 처리하려고 했습니다. 그들은 "이 숫자들의 합을 계산하다" 또는 "이 그래프에서 최단 경로를 찾다"와 같은 매우 좁은 작업에 중점을 두었습니다. 그러나 실제로 위의 여행 예와 같은 대부분의 실제 작업은 미리 정해진 워크플로우에 맞지 않습니다. 에이전틱 시스템은 실제 세계 작업의 광활한 세계를 프로그램에 열어줍니다!

## `smolagents`를 사용하는 이유는?

체인이나 라우터와 같은 일부 저수준 에이전틱 사용 사례의 경우, 모든 코드를 직접 작성할 수 있습니다. 당신이 시스템을 더 잘 제어하고 이해할 수 있게 하기 때문에 그렇게 하는 것이 훨씬 낫습니다.

그러나 LLM이 함수를 호출하도록 하거나(그것이 "도구 호출"입니다) LLM이 while 루프를 실행하도록 하는 것(다중 단계 에이전트)과 같은 더 복잡한 동작으로 이동하면, 일부 추상화가 필요합니다:
- 도구 호출의 경우, 에이전트의 출력을 파싱해야 하므로, 이 출력은 "Thought: I should call tool 'get_weather'. Action: get_weather(Paris)."와 같은 미리 정의된 형식이 필요하며, 미리 정의된 함수로 파싱하고, LLM에 제공된 시스템 프롬프트가 이 형식을 알려주어야 합니다.
- LLM 출력이 루프를 결정하는 다중 단계 에이전트의 경우, 마지막 루프 반복에서 무엇이 일어났는지에 따라 LLM에 다른 프롬프트를 제공해야 하므로, 일종의 메모리가 필요합니다.

보시겠어요? 이 두 가지 예로, 우리를 도울 수 있는 몇 가지 항목의 필요성을 이미 찾았습니다:

- 물론, 시스템을 구동하는 엔진 역할을 하는 LLM
- 에이전트가 접근할 수 있는 도구 목록
- LLM을 에이전트 로직에 안내하는 시스템 프롬프트: ReAct 루프 of Reflection -> Action -> Observation, 사용 가능한 도구, 사용할 도구 호출 형식...
- LLM 출력에서 도구 호출을 추출하는 파서, 위의 시스템 프롬프트에 표시된 형식으로.
- 메모리

그런데, 우리가 LLM의 의사 결정에 여지를 주기 때문에, 확실히 오류를 범할 것입니다: 그래서 우리는 오류 로깅 및 재시도 메커니즘이 필요합니다.

이 모든 요소들이 잘 작동하는 시스템을 만들기 위해 긴밀하게 결합되어야 합니다. 이것이 우리가 이 모든 것을 함께 작동시킬 수 있도록 기본 구성 블록을 만들어야 한다고 결정한 이유입니다.

## 코드 에이전트

다중 단계 에이전트에서, 각 단계에서, LLM은 외부 도구에 대한 일부 호출 형태로 액션을 작성할 수 있습니다. 이러한 액션을 작성하기 위한 일반적인 형식(Anthropic, OpenAI 및 많은 다른 회사에서 사용함)은 일반적으로 "도구 이름과 사용할 인수의 JSON을 작성하는 것, 그런 다음 어느 도구를 실행할지와 어떤 인수로 파싱하는 것"의 다양한 그림자입니다.

[여러](https://huggingface.co/papers/2402.01030) [연구](https://huggingface.co/papers/2411.01747) [논문](https://huggingface.co/papers/2401.00812)은 LLM의 액션을 코드 스니펫으로 작성하는 것이 더 자연스럽고 유연한 방식임을 보여주었습니다.

그 이유는 간단합니다. *우리는 컴퓨터가 수행하는 액션을 표현하도록 우리의 코드 언어를 특별히 제작했습니다*.
다시 말해서, 우리의 에이전트는 사용자의 문제를 해결하기 위해 프로그램을 작성할 것입니다: 그들의 프로그래밍이 Python 블록에서 더 쉬울 것이라고 생각하시나요, 아니면 JSON에서?

아래 그림은 [Executable Code Actions Elicit Better LLM Agents](https://huggingface.co/papers/2402.01030)에서 가져왔으며, 코드에서 액션을 작성하는 일부 이점을 설명합니다:

<img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/transformers/code_vs_json_actions.png">

JSON과 같은 스니펫 대신 코드에서 액션을 작성하면 더 나은 결과를 제공합니다:

- **구성성(Composability):** JSON 액션을 서로 중첩할 수 있거나, Python 함수를 정의할 수 있는 것과 같은 방식으로 나중에 재사용할 JSON 액션 세트를 정의할 수 있을까요?
- **객체 관리:** `generate_image`와 같은 액션의 출력을 JSON에 어떻게 저장하나요?
- **일반성:** 코드는 컴퓨터가 할 수 있는 모든 것을 간단히 표현하도록 구축되었습니다.
- **LLM 훈련 데이터의 표현:** 많은 품질의 코드 액션이 이미 LLM의 훈련 데이터에 포함되어 있으므로, 그들은 이미 이것에 대해 훈련되었습니다!
